# #1684 Host compact-diagonal null-space measurement

## Semantic and execution correspondence

TensorKit `cfaa073e4d1e3eb2167edcbdc3be9872f41e7d91` `src/factorizations/matrixalgebrakit.jl:MAK.initialize_output(qr_null!/lq_null!)` follows MatrixAlgebraKit `829bd3be` `src/interface/orthnull.jl:default_algorithm(left_null!/right_null!)`, whose no-truncation default chooses QR/LQ and therefore reports structural nullity. TeNeT's existing public contract is instead numerical rank under `σ > ε_D max(m,n)σmax`; this change preserves that intentional difference. QSpace `d2d3d7da6a59a2e8f2cb7dc8f33e7c345af59371` `Source/mpsortho.cc` has SVD orthogonalization/truncation but no corresponding public null-basis operation. An admitted compact diagonal supplies one finite scalar per aligned coordinate, so its left and right kernels are the same coordinate indices with zero magnitude. TeNeT retains the existing sector geometry, non-dual output bond, dense rectangular factor publication, lazy-adjoint redirect, checked-Generic path, and Host/CUDA capability boundary. Only the owned Host multiplicity-free compact case bypasses input densification and SVD; near-cutoff, nonfinite, and non-admitted cases still use the existing path. Direct work is `O(Σk_c + Σk_c q_c)` and output storage is `O(Σk_c q_c)`; the dense input path remains sectorwise cubic.

Baseline is TeNeT `755c2e13d7881e75ea87fd52504f5b9ed67bab06`; candidate is the commit containing this report. The same [harness](../issue_1684_null.rs) (SHA-256 `d0a1d65d553c21d60a11a0f8b5126c881009a6da80a707b5368365ec0602d44b`) and ignored `Cargo.lock` (SHA-256 `cc03b84d11f9bacff29a6dcdab1259a2349b76f9ece45a60153f421ebc5d74ae`) were used in both worktrees. Apple M4 Max, macOS 15.5 arm64, rustc 1.96.0, release/default features, Faer factorization provider, one dense thread; `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `VECLIB_MAXIMUM_THREADS`, `MKL_NUM_THREADS`, and `RAYON_NUM_THREADS` were set to 1. The baseline and candidate executable SHA-256 values were `b094653ea0af2afa88176658c0591ff0b7e4f936d51f8b29f48e9ec7c949df40` and `01fc283d0c600b1e9168ca485c8a2a4e210f9f904447a7cba126e013fb05246c`.

Each full public `left_null`/`right_null` call includes factor publication and drop. Setup is outside timing. For every case, the harness takes one first-call sample, three warmups, one allocation-counted call, then the median of seven five-call timing samples. Five process pairs were alternated B/C, C/B, B/C, C/B, B/C. [summary.csv](summary.csv) takes the median of the five process medians; the ten raw CSVs are retained here. `first_ns` is first within a shared-runtime process, not independent process cold-start latency.

The matrix covers U(1) and SU(2), f64/c64, one width-8 sector and four dual width-64 sectors, both null sides, and three storage/input regimes: a compact diagonal with exact zeros and well-separated nonzeros; its dense-materialized control; and a compact diagonal with one positive entry inside the conservative cutoff margin, which must use SVD. There are 48 cases per process. No timing threshold is used in CI.

Across the 16 direct compact cases, median speedup spans 8.61–332.7× (geometric mean 46.5×), and allocation calls and requested bytes decrease in every case. All 16 dense controls retain exactly the same allocation calls and bytes; their median speedup spans 0.985–1.010×. The 16 near-cutoff controls retain the SVD result path but pay three additional temporary allocations and 460–528 requested bytes, with median speedup spanning 0.955–1.010×. These are measured costs of the conservative admission check, not a claim of universal runtime or provider performance. The timing ranges in `summary.csv` expose run-to-run variation.
